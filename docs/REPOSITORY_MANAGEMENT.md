# 仓库管理：PR 审批与合并规则

规则来源：仓库所有者于 2026-09-29 在项目对话中明确要求，合并都需要审批，除非人明确说明无需审批。

## 默认规则

所有 PR 和分支合并都必须先取得仓库所有者或其明确委托的人类审批者的明确批准。该要求适用于所有目标分支及 merge、squash、rebase、fast-forward 等合并方式，也适用于文档、配置、修复和其他小改动。

日常修改、在工作分支提交／推送、测试、创建和维护 PR 的授权继续有效，但不包括自行合并。AI 审查结论、CI 通过、没有收到反对意见，以及“继续开发”“全权处理”等笼统授权，都不是人工批准，也不是免审批指令。不得在审批前启用自动合并、调用合并接口或执行合并命令；不得以直接推送、cherry-pick 等方式把待审变更写入 `main` 或其他集成分支来绕过审批。

## 唯一例外：人工明确豁免

仅当上述人类审批者清楚说明指定范围内“无需审批”或同等明确的意思时，才可以在该范围内省略审批。必须能识别适用的 PR、变更或持续授权范围；没有明确持续范围的单次豁免，不自动扩展到其他 PR、后续新增提交或未来任务。

有歧义时维持“待审批”，不得自行推定豁免。审批或豁免不能替代 CI、数据完整性、资源预算和科学证据要求，也不能作为擅自修改 GitHub 分支保护／规则集的授权。

## 执行与留痕

1. 审查时报告 PR 编号、目标分支、当前 head SHA、改动摘要、风险与阻塞项，以及实际检查结果和未检查的内容。将 AI 的“建议通过／建议修改”与人的最终批准分开。
2. 合并前确认人工批准或明确豁免确实适用于当前 PR 和变更范围。批准可以来自 GitHub 人工 review、明确的人工评论，或仓库所有者指定的 PR 审批对话；自动化或 Agent 不得冒充人类审批者。
3. 在 PR 中记录批准／豁免的来源、必要原文或准确摘要、审批者、时间、适用范围和当前 head SHA。只记录必要信息，不复制无关私人对话或凭据。
4. 批准后出现新增提交或范围变化时，重新审批；只有明确覆盖该变化的人工豁免才可例外。合并前再次核对 head SHA、检查状态和未解决的阻塞项。
5. 没有明确批准或有效豁免时，将 PR 保持为打开、待审批状态；不得把“已提交 PR”“AI 建议通过”或“CI 通过”报告成“已获人工批准”或“已合并”。

## 与旧授权和平台设置的关系

本规则是对既有完整项目操作授权的合并审批补充。在合并问题上，本规则优先于旧文档中的“无需逐项重复许可”或一般分支／PR 管理授权；不改变既有预算、数据隔离和科学验收门槛。

本文件及 `AGENTS.md`、`README.md`、`configs/resources.yaml` 是治理约束，不会自行启用 GitHub 的分支保护或规则集。平台是否强制要求 review，应以实际仓库设置为准；不得仅因文档已更新就声称平台已强制执行。
