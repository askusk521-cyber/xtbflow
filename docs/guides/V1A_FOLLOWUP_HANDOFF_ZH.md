## 0. 为什么有这份交接

V1a 正式筛查给出 `GO_V1b`（P=342 个母体，G=70 个分子式组，3 个训练 seed）。主比较 B1−A2 的 AUC 差为 +0.0931，机制对比 M₀、Mᵣ 均约 +0.021。不过同一份报告里还有三件事，决定了下一步该花钱认证什么：

1. 无引导并联 B0 的 AUC 最高（0.4945），B1−B0 = −0.229。
2. B1−A2 的差值集中在 A2 因轮次结构而几乎没有完成候选的预算点：预算 4、8、32 处，A2 的完成候选分别只有 0.0、0.0、2.5 个。预算 16 和 64 处，差值只有约 +0.04。
3. 按完成候选数粗略对齐后，B0 的优势几乎全部来自"每个候选的成本只有 A0 的一半"。按单个候选算，事件引导的增益（A1 相对 A0）看起来大于几何引导的增益（B1 相对 B0）。

V1a 正式报告中的五臂曲线如下（母体×三 seed 平均），这也是本交接的复现目标：

本交接回答三个问题：

- **任务 R**：候选数相同时，以及把验证成本算进去以后，各臂谁更好？不需要新算力。
- **任务 N**：串联用同样多网络调用时，B0 的预算优势还在不在？只做推理。
- **任务 V**：V1b 阶段 B 应该认证哪几臂、估计哪些量？只改设计文档，不跑量化。

## 1. 硬性规则

1. **不改动 V1a 正式结论。** 不修改 `docs/evidence/v1a/formal/` 下的任何文件、冻结配置、检查点和分析函数。新产出只写进新目录。
2. **全部结果标为探索性。** 正式集已经揭盲过一次，这里的任何结果都不能当作确认性证据。论文主张最终需要用新的留出集或 OOD 集确认。每份报告的首句都要写明这一点。
3. **先冻结分析配置，再碰正式数据。** 每个任务先提交一个配置 JSON，把比较对象、阈值、网格和区间方法写死，记录提交号后再运行。结果出来后若发现配置需要改，开新版本，两版都报告。
4. **不做任何新的量化计算**，xTB、DFT、MLIP 都不做。任务 N 只做生成模型推理。
5. **复用 V1a 已有函数**（代理匹配、自同构、前缀截取、`cluster_summary` 等），不重写，不新增治理类基础设施。
6. **不实现任何物理引导。** 方向规划里的 E2b 写法有已知缺陷：对 E(x̂₁)−E(x_R) 做梯度下降，会把几何推向极小点而不是鞍点；SMC 按 exp(−βΦ) 重采样也有同样的问题。物理引导要先单独出设计（采用鞍点感知方向，如仓库已有的 G_sad；或者只用于淘汰和排序，并配 TS 性检查），不在本交接范围内。
7. **每个任务一个分支、一个 PR**，基于 PR #106 的头提交；若届时已合并，则基于 main。按仓库 CLAUDE.md/AGENTS.md 的要求附中文说明、贴验收输出，不自行合并。
8. **数据在 n2 上。** 原始候选流和 V1b 源总体（1,710 个 bundle）都在 n2 的运行目录里。分析尽量在 n2 上用 CPU 跑（经 Slurm），只把小于 1 MB 的汇总结果带回仓库。

**遇到以下情况必须停下来问负责人：**

- 从原始候选流复现不出第 0 节的表：与 `gate.json` 或报告底层数值的偏差 >1e-6。
- 候选流的哈希与 `freeze.json`/`SHA256SUMS` 不符。
- 任务 N 预估超过 20 GPU 小时。
- 需要改动本交接规定的定义、比较对象或决策规则。

### R2. 三个定义

**验证单元。** 候选流按逻辑完成顺序逐个处理，给每个候选标记它是否"开启一个新的验证单元"：

```python
def opens_verification_unit(cand, earlier_units, mode, rmsd_cut=0.30):
    """earlier_units：同一 (parent, arm, seed) 流里此前已开启的单元。

    非法或 fallback 候选返回 False：它们在量化前就会被丢弃，只计生成成本。
    D1：该 channel_id 第一次出现时才开启新单元。
    D2：channel_id 未出现过，或与此前同 channel 单元的最小 RMSD > rmsd_cut 时开启新单元。
        RMSD 沿用 V1a 代理匹配的规则：允许反应物自同构，只允许真旋转，
        事件与坐标使用同一个原子映射。
    """
```

**分析 A：按候选数对齐。** 对每个 (parent, arm, seed)，取最大预算流的前 n 个完成候选，判断是否命中。

- 若该流的总候选数 < n，这个单元在 n 处记为删失。
- 成对比较时，在 n 处只使用两臂都未删失的 (parent, seed)；先在母体内对可用 seed 求平均，再计算母体差。
- 某个 n 处可用母体不足 80% 时，照常报告，但标注"覆盖不足"。
- 同时报告被删失母体的原子数分布：大分子更容易被删失，会带来选择偏差。

**分析 B：计入验证成本的预算。** 给定 κ（每个验证单元折合多少个网络调用单位），候选 j 完成时的累计总成本为：

```
total_cost(j) = completion_units(j) + κ × verification_units_opened_up_to(j)
```

- **预算点**：T_κ(k) = k × (50 + κ)，k ∈ {4, 8, 16, 32, 64}，含义是"k 个各做一次验证的 B0 等效候选"。
- **第二个复现检查**：κ=0 时 T 与 V1a 的 C(k) 相同，所以 κ=0 时的 AUC_κ 必须精确等于 V1a 的 AUC。
- **删失**：某臂的流在 T_κ(k) 之前就已用完，该格记为删失。
- **入选规则**：一个预算点只有在比较集中每一臂的删失比例都 ≤5% 时，才进入 AUC_κ；权重在入选点上重新归一化，并在报告中列出每个 κ 实际用了哪些点。
- **已知局限**：κ 对所有分子取同一个常数。真实的验证成本随分子大小变化，这一点要写进报告。

### R3. 要报告的内容

1. **分析 A**

3. **单位换算**：用开发期成本标定文件（`cost_calibration.json`）中 f 单次前向的实测 GPU 时间，把 κ 和 κ\* 换算成"GPU 秒/验证单元"，方便负责人与真实验证成本（MLIP TS 优化加 IRC、DFT）对照。本任务不测量真实验证成本。

## 3. 任务 N：NFE 对齐的串联对照（可与 R 并行）

**分支：** `v1a-n/nfe-control`。**输出目录：** `docs/evidence/v1a_n/`。**算力：** 只做推理，先测速再定规模。

**要回答的问题：** V1a 中 B0 每个候选做 50 次联合网络调用，A0 则是事件 50 次加几何 50 次。B0 的预算优势，究竟来自联合生成本身，还是只是因为串联多跑了一倍步数？

**新增两臂**（全部无引导，使用 V1a 冻结的检查点，3 个训练 seed，采样 seed 0）：

| 臂 | 做法 | 单候选网络调用 |
|---|---|---|
| A0-25+25 | g 积分 25 步 → 解码 → h 积分 25 步 | 25×w_g + 25×w_h |
| B0-25 | 在冻结路径上联合积分 25 步 | 25 |

现有的 A0（50+50）和 B0（50）候选流直接复用，不重跑。

**步骤：**

1. 从冻结成本表读出 w_g、w_h，确认 A0-25+25 的单候选成本与 B0-50 相等或接近，并写进报告。相差超过 10% 时在报告中说明，比较时以实际成本记账。
2. 给候选流生成脚本加上 `--nfe-event`、`--nfe-geometry`、`--nfe-joint` 覆盖参数。默认值保持不变，冻结配置不受影响；实际使用的覆盖值写进输出元数据。积分仍按相邻网格的实际时钟差进行。
3. 在 10 个开发母体上做冒烟测试，检查：步数正确、Δt 之和为 1、解码与代理匹配正常、新输出不覆盖任何已封存目录。同时测速并预估全量所需 GPU 小时，超过 20 小时就停下来问。
4. 先冻结配置 `configs/v1a_n/nfe.json`（臂、步数、成本表哈希、比较对象、区间方法），再在 V1a 正式集的 342 个母体上运行。噪声寻址沿用 `efficiency` 命名空间的语义键，使新臂与原臂共享起点噪声。
5. 用 V1a 的同一套代理评估、5 个预算点和 AUC 定义计算结果，再用任务 R 的分析 A 代码做按候选数对齐的比较。

**预先写定的解读：**

- **主对比**：AUC(B0-50) − AUC(A0-25+25)，按母体配对，给出 95% 聚类区间。
  - 区间下限 > 0：在这个对照下，"并联每次调用更省"仍然成立。
  - 区间包含 0 或整体为负：V1a 中 B0 的预算优势可以由步数解释，不能归功于联合生成。
- **次要**：在同样候选数下，A0-25+25 相对 A0-50+50、B0-25 相对 B0-50 各损失多少命中率。这说明两种架构对步数的敏感程度。

**验收：** 冒烟测试与新增单元测试通过；新臂的结果行与原五臂表格式一致；报告首句写明"探索性"和主对比结论。

## 4. 任务 V：V1b 修订草案 v2.2（R 完成后做，只写文档）

**分支：** `v1b/amend-v2.2`。**输出：** `docs/v1b/AMENDMENT_v2.2_ZH.md`，以及 `configs/v1b/audit.json` 的对应修改。**不运行任何量化；负责人批准前，V1b 不冻结。**

现行 V1b v2.1 的阶段 B 只认证 A2 和 B1，估计 Δ^cert(B1−A2)。按第 0 节的结果，这恰好是信息量最少的一对。修订内容在本交接中写死。任务 R 的结果只用来估计成本与方差、决定样本分配，**不能用来挑选估计量**。

1. **阶段 A 不变**，仍是五臂候选级分层审计。
2. **阶段 B 认证四臂**：A1、A2、B0、B1。
3. **主决策不变**：Δ^cert(B1−A2)，预算 16，训练 seed 0，决策规则同 v2.1 第 10.5 节。这保证 V1b 仍完成它原来的任务：认证 V1a 的 GO。
4. **关键次要估计量**（报告区间，不设闸门）：

   - S2：Δ^cert(B1−A1)，预算 16。
   - S3a：B1 与 B0 的同候选数比较。每个母体取 n_p = B1 在预算 16 处的完成候选数，B0 只用其流中前 n_p 个候选。

   - `primary_empty_secondary_nonempty`：B1、A2 的 C\* 为空，但 B0 或 A1 的非空。这一层抽样认证。

   主估计量的 HT 权重不变，有效性不受影响；次要估计量用同一套包含概率估计。次要估计量没有按 B0/A1 的命中模式分层，方差可能偏大，报告时注明。
6. **成本超限时的删减顺序（预先写定）**：
   - 先删 S1：认证 B0 的 16 个候选最贵，而生成成本视角已经可以由 V1a 代理结果和阶段 A 的 PPV 回答。
   - 再删 S2。
   - S3a、S3b 保留：验证成本占主导时，比的就是单个候选的质量。
7. **重算资源表**：按 v2.1 第 13 节，用 D1 实测的链成本和任务 R 给出的各臂 |C\*| 分布，给出中位估计与保守上限。
8. **导出截取集合**：V1a 导出的源总体里还没有"B0 前 n_p 个候选"的截取集合。草案要写明从冻结源总体推导它的规则（按逻辑完成顺序截取），并在 D0 冻结时一并导出、记录哈希。

**验收：** 草案逐条对应以上 8 点；`audit.json` 的修改通过现有配置校验；明确列出相对 v2.1 改了哪些条目、哪些没改。
